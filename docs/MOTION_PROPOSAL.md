## 1. 제안의 핵심

**동작 프리셋의 종류를 늘리기보다, 다양한 연출을 동일한 신체·접촉·시간 관계로 표현하고 검증하는 공통 기반을 우선 구축한다.**

사용자는 “화를 참다가 일어나 몇 걸음 나간 뒤, 돌아서서 두 사람을 따진다”처럼 지시한다. 이 지시를 특정 동작 이름들의 조합으로만 번역하면, 접지·균형·연기 연결·상대 배우의 반응을 에이전트가 매번 수작업으로 보정하게 된다.

권장 처리 구조:

```text
사용자의 자연어 연출
  → 편집 가능한 연출 계획: 의도·주의 대상·사건·유지 조건
  → 동작 계획: 이동·지지 전환·접촉·타이밍
  → 리그별 제약 풀이와 동작 생성
  → 결정론적 평가 및 접촉·연속성 검사
  → 실제 렌더 검토
  → 원하는 부분만 수정하고 재계산
```

자연어 해석과 연출 선택은 유연하게 두되, 리그 해석·접촉 유지·시간 연결·재계산의 규칙은 엔진이 책임지는 구조를 제안한다. 초기 구현부터 물리 시뮬레이터나 학습 모델이 필수인 것은 아니다.

## 2. 관찰 범위와 책임 구분

이 문서는 연결된 MCP 도구, 실제 생성된 장면과 MP4, 로컬 설치 번들에서 확인한 구현을 바탕으로 한다. 전체 저장소·개발 브랜치·미공개 기능을 조사한 결과는 아니다. “미노출”은 이번 세션에서 사용 가능한 MCP 계약에 없었다는 뜻이며, 제품 전체에 해당 기능이 없다고 단정하지 않는다.

이번 제작은 **기존 리그를 사용했다.** 새 캐릭터 리그나 모션캡처를 도입하지 않았다. 기존 관절에 회전·골반·위치 트랙을 작성했고, 후반에는 실제 리그 치수를 읽어 발의 목표 위치에서 다리 각도를 역산했다. 확인된 기준 신장은 1.72m, 허벅지 관절 간 길이는 0.44m, 종아리는 0.41m였다. 이는 해당 리그의 값이며 모든 모델에 적용할 상수가 아니다.

문제에는 에이전트의 작성 실수도 포함된다. 초기에는 실제 치수와 다른 값으로 계산했고, 몸의 위치를 걸음마다 감속시키는 곡선을 사용했으며, 세 배우의 반응을 비슷한 시점에 배치했다. 따라서 제안 목표는 “엔진이 모든 연출을 대신 선택한다”가 아니라 **작성자가 실수하기 어려운 계약과, 실수를 발견·수정하기 쉬운 도구**를 제공하는 것이다.

## 3. 사례에서 드러난 문제

| 실제 증상 | 확인된 원인 또는 작성상의 한계 | 수행한 보정 | 필요한 공통 기능 |
|---|---|---|---|
| 걷는 몸이 걸음마다 멈춰 로봇처럼 보임 | 에이전트가 각 이동 구간에 시작·종료 감속을 반복 적용 | 이동 곡선의 중간 속도를 연속적으로 연결 | 경로와 보행의 공동 계획, 속도·가속도 검사 |
| 발이 떠 있거나 미끄러짐 | 초기 계산의 리그 치수 오차, 골반 이동과 발 목표의 불일치 | 실제 치수 기반 IK, 지지 발 목표 고정 | 리그 조회, 접촉 제약, 전신 보정 |
| 접지 보정 후 회전이 잔걸음처럼 부자연스러움 | 평발 고정을 강하게 유지하며 회전을 분할 | 시선·상체 선행, 앞꿈치 지지와 발 교체 | 접촉 모드 전환, 회전 허용 범위, 동작 단계 연결 |
| 세 사람이 같은 자세로 앉음 | 같은 기본 포즈로 시작, 인물별 상태를 충분히 지정하지 않음 | 손·발 배치와 상체 기울기를 분리 | 인물별 지속 상태와 자세 제약 |
| 두 사람이 인형처럼 정지함 | 주인공의 이동에 비해 상대의 주의·반응 계획이 부족 | 시선 추적과 서로 다른 시점의 자세 변화 | 사건 기반 반응, 주의 대상 |
| 반응을 추가하자 손이 함께 올라가 춤처럼 보임 | 팔 키프레임 전환과 반응 시점이 겹침 | 손을 허벅지에 유지하고 반응을 고개·몸으로 제한 | 접촉 유지, 제스처 예산, 다인 동시성 진단 |
| 상체를 바꾸면 손이 허공에 뜸 | 팔 각도만 지정해 손과 허벅지 관계가 유지되지 않음 | 상체 위치에 맞춰 팔 IK 재계산 | 이동하는 신체 표면에 대한 상대 접촉 |
| 걷기 길이를 바꾸면 컷·시선·반응 시간을 다시 수정해야 함 | 절대 초 단위의 느슨한 연결 | 다수의 시작·종료·키 시간을 수동 이동 | 의미 있는 사건과 시간 의존 관계 |
| 클로즈업을 조정하자 앞사람 몸이 피사체를 가림 | 골격 프리뷰만으로 최종 가림을 충분히 확인하지 못함 | 실제 렌더 후 카메라 재배치 | 실제 렌더 검토, 피사체 가시성 검사 |

확인한 기본 보행 포즈 생성은 시간에 따른 주기적인 관절 회전을 사용한다. 이동 액션과 포즈를 작성할 수 있지만, 이번 MCP 계약만으로는 발 지지와 몸 이동의 일치를 명시적으로 요청·검증하기 어려웠다. 이 경계를 공통 엔진 기능으로 보완할 필요가 있다.

| P0-B | 동작 진단과 실제 렌더 검토 | 미끄러짐·관통·급정지를 수정 전에 발견 | P0-A, 렌더와 동일한 평가기 |

| P1-C | 부분 재생성·잠금·레이어 계약 | 잘 나온 연기는 보존하고 문제 구간만 수정 | 리비전 관리, 제약 풀이 |

P0-A/B는 P0-C를 개발하고 검증하기 위한 선행 기반이다. 다만 사용자가 체감할 첫 출시 단위는 **“접촉을 유지한 자세 수정과 그 결과 검사”**까지 묶는 편이 좋다. 조회 API만 추가해서 자연스러운 동작 생성이 해결됐다고 보아서는 안 된다.

## 5. P0-A — 공식 리그·표면·상태 조회

### 엔진 요구사항

- 관절 계층, 바인드 변환, 길이, 회전 순서, 축, 한계, 캐릭터 스케일을 반환한다.
- 발뒤꿈치·앞꿈치·발바닥·손바닥 같은 기준점과 접촉 면적을 제공한다.
- 허벅지·좌석·팔걸이처럼 접촉 대상으로 쓸 표면을 안정적인 ID로 노출한다.
- 지원하지 않는 관절·접촉 기준점은 추정값과 구분해 표시한다.
- 자유로운 리그 이름을 `left_foot`, `pelvis` 등의 의미 역할에 매핑하되 원본 ID를 보존한다.

### 제안 MCP

| 도구 | 주요 입력 | 주요 출력 |
|---|---|---|
| `get_capabilities` | 요청할 스키마 버전 | 지원 제약·리그 기능·평가·렌더 옵션, 엔진 버전 |
| `inspect_rig` | 장면 참조, 배우 ID | 관절·축·한계·치수·접촉 패치·바인드 상태 |
| `inspect_surfaces` | 장면 참조, 객체 ID 목록 | 표면 ID·변환·영역·충돌 지원 범위 |
| `evaluate_motion` | 장면 참조, 구간·샘플률·대상 | 관절/접촉점의 월드 변환, 속도, 활성 제약·접촉 |

`evaluate_motion`은 현재 `evaluate`의 확장으로 구현해도 된다. 특히 **발 위치·발바닥 방향·속도**를 선택적으로 조회할 수 있어야 한다. 데이터가 많으면 요약·구간 페이지·다운로드 아티팩트로 나누고, 수천 프레임을 기본 응답에 모두 넣지 않는다.

### 완료 기준

- 동일 장면·엔진 버전·리비전에서 평가와 렌더가 같은 골격 상태를 사용한다.
- 관절 이름을 모르는 에이전트가 공식 조회만으로 발바닥과 손바닥을 식별할 수 있다.
- 신장·다리 비율을 바꿔도 하드코딩한 기본 리그 길이에 의존하지 않는다.

## 6. P0-B — 진단은 점수보다 원인과 위치를 반환

### 진단 항목

- **접촉 이동:** 지지 구간의 접촉점이 기준 표면에서 이동한 거리.
- **관통·이격:** 접촉 모드에 맞는 발/손 표면과 대상 표면 사이 거리.
- **연속성:** 위치·속도·가속도·각속도의 급격한 변화와 발생 구간.
- **관절 한계:** 한계 초과, 도달 불가능한 목표, 지나친 보정량.
- **지지 상태:** 지지 영역과 몸의 무게중심 추정의 관계. 질량 모델이 없는 경우 운동학적 근사라고 표시한다.
- **렌더 가시성:** 중요 배우의 얼굴·손·발이 다른 객체나 프레임 경계에 가려지는 구간.
- **다인 동시성:** 연출상 연결되지 않은 배우들의 큰 제스처가 동시에 시작하는 구간. 오류 확정이 아닌 검토 경고로 제공한다.

### 제안 MCP

`analyze_motion(scene, range, profiles, tolerances)` → 구조화된 진단 목록, 관련 ID·구간·측정값·기준값·권장 수정 방향.

`render_review(scene, range, cameras, overlays, sampling)` → 실제 렌더의 정속/슬로모션 영상, 접촉·궤적 오버레이, 대표 프레임.

골격 프리뷰와 실제 렌더 결과를 명확히 구분한다. 접촉점만 맞았다고 메시 표면까지 맞았다고 보고하지 않는다. foot-lock 오차가 작아도 리듬·회전·상대 반응이 자연스러운지는 별도 시각 검토가 필요하다.

### 완료 기준

- 알려진 미끄러짐·관통·급정지 fixture를 주입하면 대상과 구간을 반환한다.
- 이동 중인 발을 지지 발로 오인하지 않으며, 앞꿈치 피벗을 평발 미끄러짐으로 오인하지 않는다.
- 검사 불가 항목은 `not_evaluated`와 이유를 반환한다.

## 7. P0-C — 접촉과 지지 상태를 보존하는 제약 풀이

### 공통 제약

| 제약 | 역할 | 이번 사례의 적용 |
|---|---|---|
| `contact` | 두 표면 사이 위치·방향·허용 자유도 유지 | 지지 발–바닥, 손바닥–허벅지 |
| `support` | 어떤 접촉이 몸을 지지하는지 지정 | 일어서기·걷기·회전의 지지 전환 |
| `look_at` | 머리·목·눈의 가능한 범위에서 주의 대상 추적 | 걸어 나가는 사람 따라보기 |
| `reach` | 접촉 전 접근·도달 목표 | 손을 무릎에 내려놓기 |
| `joint_limit` | 리그 관절 한계 준수 | 무릎·발목의 비정상 회전 방지 |
| `preserve` | 승인한 궤적·자세·접촉·구간 보호 | 다른 배우의 손 위치 보존 |
| `clearance` | 충돌·관통 회피 | 소파에서 일어나 앞 공간으로 이동 |

`contact`에는 기준 좌표계가 필요하다. 바닥 접지는 월드/바닥 로컬 기준, 손–허벅지 접촉은 움직이는 신체 표면 로컬 기준이다. 모델 스케일·표면 회전·상체 변화에도 의미가 유지되어야 한다.

접촉 모드는 최소한 **평발, 뒤꿈치, 앞꿈치 피벗, 비접촉**을 구별한다. 회전을 전부 금지하면 뒤돌기가 부자연스러워진다. 모드별로 접촉 영역과 허용 회전·미끄러짐을 지정하고, 전환 구간을 블렌드한다.

### 제안 MCP

`solve_motion(scene, range, constraints, objectives, preserve, seed)`

반환값은 수정된 장면 리비전 또는 패치, 풀이 상태, 제약 잔차, 접촉 일정, 평가 결과를 포함한다. 목표를 달성할 수 없으면 조용히 무시하지 않는다. 어떤 조건끼리 충돌하는지와 시간·도착 위치·접촉 중 무엇을 완화할 수 있는지 반환한다.

우선순위가 다른 조건을 구분한다. 예를 들어 바닥 관통 금지는 강한 조건이고, “0.1초 안에 돌아서기”는 도달 불가능할 때 조정 가능한 연출 목표일 수 있다. 자동 완화는 요청에 명시된 항목만 허용한다.

### 완료 기준

- 상체 기울기를 바꿔도 손바닥–허벅지 접촉이 허용 오차 안에 남는다.
- 리그 스케일·골반 높이·이동 속도를 바꿔도 지지 발의 접촉이 유지된다.
- 앞꿈치를 축으로 돌아설 때 발바닥 전체 고정을 강제하지 않는다.
- 실행 불가능한 조건 조합은 `infeasible`과 원인 목록을 반환한다.

## 8. P1-A — 이동과 보행을 공동 계획

보행 포즈와 루트 이동을 서로 독립적으로 작성하는 대신, 목적지·도착 구간·속도 성향·가용 공간·리그·접촉 조건에서 발 디딤과 몸 이동을 함께 산출한다.

사용자 입력은 “두 걸음으로 급히”, “망설이며”, “한쪽 다리에 무게를 덜 싣고”처럼 열려 있을 수 있다. 내부 표현은 발 디딤 위치, 지지 시간, 허용 하중, 발 방향, 관절 가동 범위, 선호 속도·보폭 등의 연속적인 값과 제약으로 정규화한다.

예를 들어 팔자걸음은 발의 선호 진행각과 고관절 회전 특성으로, 한쪽 다리의 불편함은 지지 시간·하중·가동 범위의 비대칭으로 표현할 수 있다. 이 표현만으로 모든 임상적 보행을 정확히 재현한다고 보장하는 것은 아니며, 해당 표현을 생성·보정·검증하는 공통 계약이 목적이다.

### 제안 MCP

`plan_motion`은 선택된 연출을 해석 가능한 계획으로 반환한다. 계획에는 경로, 속도 곡선, 지지/이동 단계, 발 디딤 후보, 예상 사건이 포함된다. `solve_motion`은 그 계획을 리그에 적용한다. 두 단계는 하나의 도구 내부에서 실행할 수 있지만, 계획 자체는 조회·수정할 수 있어야 한다.

### 완료 기준

- 거리·도착 시간 변경 시 보폭이나 걸음 수를 재계산한다.
- 의도한 망설임이 아닌 구간에서 걸음마다 루트 속도가 0으로 떨어지지 않는다.
- 급정지·느린 출발·비대칭 지지 같은 변형을 동일한 제약 체계로 처리한다.
- 좁은 공간 때문에 목표를 달성할 수 없으면 대안과 변경량을 반환한다.

## 9. P1-B — 사건 기반 시간 그래프

절대 시간은 지원하되, 주요 연기와 편집은 사건에 연결할 수 있도록 한다.

```text
stand.begin
  → left.notice (+ 짧은 지연)
  → walk.first_contact
  → walk.final_settle
  → turn.begin (+ 망설임)
  → turn.face_partner
  → point.begin
  → camera.cut_to_reaction
```

사건은 계획 단계의 예상값과 최종 풀이 이후의 확정값을 구분한다. 발 디딤 수가 바뀌어 중간 사건이 사라지더라도 `final_settle` 같은 의미적 앵커는 유지할 수 있어야 한다.

### 제안 MCP

- `inspect_timeline`: 사건·액션·컷의 관계와 현재 확정 시간을 조회.
- `retime`: 도착 시간이나 구간 길이를 수정하고 종속 요소를 재계산.
- `patch_scene`: 사건 참조를 포함한 편집을 리비전 단위로 적용.

### 완료 기준

- 걷기를 늘리면 회전·손가락질·리액션 컷이 정의한 관계에 맞게 이동한다.
- 사건 ID를 보존하고, 끊어진 참조와 시간 의존 순환을 오류로 반환한다.
- “먼저 보기 → 몸 돌리기 → 발 옮기기”의 선후관계를 유지한다.

## 10. P1-C — 부분 재생성, 잠금, 레이어 우선순위

사용자는 “다른 건 그대로 두고 걷기만”이라고 지시할 수 있어야 한다. 이때 무엇이 실제로 보존되는지 명확해야 한다.

- 보호 범위: 배우, 신체 부위, 접촉 관계, 카메라, 구간, 사건.
- 재계산 영향 범위: 변경으로 인해 조정이 필요한 요소를 미리 반환.
- 원자적 적용: 기대 리비전과 맞을 때만 패치를 적용.
- 되돌리기와 후보 분기: 이전 장면으로 복원하거나 A/B 비교.
- 우선순위: 수동 키프레임, 제약, 절차적 모션, 제스처가 충돌할 때 승자와 이유를 조회.

현재도 액션 삭제·수정과 트랙 기반 보정이 가능하다. 제안은 이를 대체하기보다, **풀이 대상·보호 조건·충돌 진단이 포함된 재생성 계약**을 추가하는 것이다.

잠금과 새 목표가 양립하지 않으면 보호된 결과를 몰래 수정하지 말고 충돌을 반환한다. 양팔이 잠겼는데 팔 동작이 필요한 균형 보정을 요청한 경우가 예다.

## 11. P1-D — 배우별 상태와 인과적인 반응

배우마다 다음 상태를 유지한다.

- 현재 자세와 유지할 접촉
- 현재 주의 대상
- 행동 의도와 반응의 원인
- 움직여도 되는 부위와 움직임의 크기
- 이미 진행 중인 행동과 중단 가능한 시점

“반응하라”를 큰 제스처로 바로 번역하지 않는다. 예를 들어 `hands_resting`, `attention_to_partner`, `small_posture_adjustment`는 특정 연기 이름보다 지속 상태에 가깝다. 사용자는 내부 명칭을 알 필요 없이 “손은 그대로 두고 고개만 따라가”라고 수정할 수 있다.

### 제안 MCP

`plan_performance(scene, direction, actor_context, preserve)` → 배우별 의도, 주의 대상, 사건 연결, 허용 움직임, 선택한 해석과 대안.

이 단계는 확률적인 자연어 해석을 포함할 수 있다. 그러나 선택된 계획은 저장되어야 하며, 이후 `solve_motion`은 버전과 seed를 고정해 재현 가능해야 한다. 모든 호출에서 장면 전체를 새로 해석하지 않는다.

### 완료 기준

- “계속 듣기”를 무동작 또는 미세한 시선·자세 반응으로 표현할 수 있다.
- 상대가 움직이기 전에 원인 없는 큰 반응이 먼저 시작되지 않는다.
- 동시 동작을 원하지 않는 지시에서 여러 배우가 같은 시점에 손을 들지 않는다.
- 손 접촉을 유지하면서 서로 다른 몸·고개 반응을 만들 수 있다.

## 12. 제안 MCP 계약 예시

아래 이름·필드는 **신규 인터페이스 제안**이며 현재 지원되는 호출이 아니다. 계약을 논의하기 위한 예시로, 완전한 JSON Schema는 아니다.

### 접촉을 유지한 보행 계획과 풀이

```json
{
  "tool": "solve_motion",
  "arguments": {
    "schemaVersion": "proposed-1",
    "sceneRef": {"id": "sofa-scene", "revision": 12},
    "actor": "center",
    "range": {"fromEvent": "stand.end", "toEvent": "walk.final_settle"},
    "planRef": "plan-walk-03",
    "constraints": [
      {"id": "floor-clearance", "type": "clearance", "subject": "center", "surface": "floor", "priority": "required"},
      {"id": "stance-contact", "type": "contact_schedule", "scheduleRef": "plan-walk-03.contacts", "priority": "required"},
      {"id": "joint-limits", "type": "joint_limit", "source": "rig", "priority": "required"}
    ],
    "objectives": {"continuousRootVelocity": true, "minimizePoseChange": true},
    "preserve": [
      {"actors": ["left", "right"], "scope": "all"},
      {"scope": "camera_geometry"}
    ],
    "allowedRelaxations": ["arrival_time"],
    "seed": 7
  }
}
```

접촉 조건은 항상 발바닥 전체를 고정하는 대신, 계획이 반환한 접촉 스케줄을 참조한다. 손·발·표면 식별자는 `inspect_rig`와 `inspect_surfaces`의 반환값을 사용하며 이름을 추측하지 않는다.

### 손–허벅지 접촉 유지

```json
{
  "id": "left-hand-rest",
  "type": "contact",
  "subject": {"actor": "left", "patch": "palm_left"},
  "target": {"actor": "left", "surface": "thigh_left"},
  "frame": "target_local",
  "mode": "rest",
  "active": {"fromEvent": "scene.begin", "toEvent": "scene.end"},
  "tolerances": {"separationMeters": 0.005},
  "priority": "required"
}
```

### 구조화된 결과와 실패

```json
{
  "status": "solved",
  "sceneRef": {"id": "sofa-scene", "revision": 13},
  "engineVersion": "<reported-by-runtime>",
  "solverVersion": "<reported-by-runtime>",
  "patchRef": "patch-13",
  "changed": {"actors": ["center"], "rangeSeconds": [1.7, 4.8]},
  "events": {"walk.final_settle": 4.8},
  "relaxed": [{"field": "arrival_time", "deltaSeconds": 0.2}],
  "diagnostics": [],
  "artifacts": [{"kind": "motion_report", "ref": "report-13"}]
}
```

`solved`는 허용 조건을 만족한 풀이 결과이며 예술적으로 자연스럽다는 보증이 아니다. 실패 시 `infeasible`, `unsupported`, `revision_conflict` 등을 구분하고 `constraintIds`, `range`, `reason`, `suggestedRelaxations`를 반환한다. 임계값 초과 진단을 숨긴 채 성공으로 처리하지 않는다.

## 13. API 운영·호환성 원칙

- 기존 `run_script`, `apply_addon`, `evaluate`, `preview`, `render_video`, `open_link` 흐름은 유지한다.
- 사람이 읽는 설명과 별개로, 장면·패치·진단은 MCP의 구조화된 결과로 반환한다. 설명 텍스트에서 `spec:` 이후를 잘라 파싱하지 않아도 되어야 한다.
- 작은 작업은 inline spec, 큰 작업은 장면/아티팩트 참조를 지원한다. 고밀도 관절 트랙을 매번 대화 컨텍스트로 왕복시키지 않는다.
- 좌표계, 거리 단위, 각도 단위, 회전 순서, 시간 기준을 계약에 명시한다.
- 해결기·엔진·리그 버전과 seed를 기록한다. 학습 모션을 사용하면 모델·클립 버전도 기록한다.
- 긴 렌더/풀이에는 job ID, 단계, 취소, 재연결 가능한 상태 조회를 제공한다. 완료 전 파일이 존재한다고 가정하지 않는다.
- 액션·제약·사건에 안정적인 ID를 부여한다. 배열 위치 기반 이름에만 의존하지 않는다.
- 결과에는 승인하지 않은 변경, 자동 완화, 평가하지 못한 항목을 명시한다.

## 14. 회귀 시나리오와 제안 수용 기준

다음 수치는 개발 논의를 위한 **초기 허용치 제안**이다. 실제 리그·메시·렌더 정확도로 검증해 조정해야 한다.

| 시나리오 | 자동 검증 | 시각 검토 |
|---|---|---|
| 세 사람의 소파 장면 | 모든 사건 참조 유효, 보호된 두 배우의 발·손 접촉 보존 | 원인 없는 동시 손짓 없음, 주인공의 이동에 대한 개별 반응 |
| 거리·시간 변경 보행 | 필수 정지가 없는 중간 접촉에서 루트 속도 불연속 검사 | 걷다 서다 반복하지 않음 |
| 다른 신장·다리 비율 | 지지 접촉점 이동/이격 각각 5mm 이내를 초기 목표로 설정 | 발이 뜨거나 바닥을 통과해 보이지 않음 |
| 앞꿈치 피벗 | 피벗 접촉 유지, 허용 회전 준수, 무릎 한계 준수 | 평발 회전이나 잔걸음 반복처럼 보이지 않음 |
| 손을 둔 채 몸 기울이기 | 신체 로컬 표면 접촉 유지 | 손이 허공에 뜨거나 허벅지를 뚫지 않음 |
| 도착 시간 재지정 | 종속 사건·컷 재타이밍, 참조 손실 없음 | 회전·항의·리액션의 순서 유지 |
| 불가능한 시간·잠금 조합 | `infeasible`, 충돌 조건·대안 반환 | 무리한 관절 꺾임으로 억지 해결하지 않음 |
| 특정 구간만 재생성 | 보호 대상의 트랙/평가값 변경 없음 | 앞뒤 연결이 튀지 않음 |

검사 기준은 접촉 유형별로 다르게 적용한다. 스윙 발은 바닥에서 떠 있어야 하고, 피벗 발은 회전할 수 있다. 동적인 균형을 단순한 정적 지지다각형 규칙으로 무조건 금지해서도 안 된다.

## 15. 현실적인 개발 단계

1. **측정 가능한 기반:** 리그·표면 조회, 월드 접촉점 평가, 진단 리포트, 실제 렌더 검토. 본 장면을 회귀 fixture로 저장한다.
2. **접촉을 유지한 편집:** 손–허벅지, 평발–바닥부터 구현하고, 앞꿈치/뒤꿈치 모드와 전신 보정을 추가한다.
3. **연결된 동작 생성:** 경로·접촉 일정·속도를 함께 계획하고, 사건 기반 재타이밍과 부분 재생성을 연결한다.
4. **다인 연출:** 배우별 지속 상태와 인과적 반응 계획, 카메라 가시성 진단을 통합한다.
5. **품질 확장:** 동일한 계획/제약 표현 위에 모션 클립, 학습 기반 생성, 더 정교한 역학 모델, 후보 비교를 연결한다.

처음부터 수백 개의 연기 프리셋이나 완전한 물리 시뮬레이터를 만들기보다, **“자세를 바꿔도 접촉이 유지되고, 시간을 바꿔도 관계가 유지되며, 문제가 생기면 위치와 원인이 보이는가”**를 첫 제품 목표로 삼는 것을 권한다.

## 16. 사례 자료

워크스페이스에 보존된 아래 파일을 개발 검토 자료로 사용할 수 있다. 이 제안서를 외부에 전달할 때 필요한 영상만 별도로 첨부한다. 파일명은 식별용이며 개발자의 환경에 존재한다고 가정하지 않는다.

- `sofa-confrontation-drama.mp4`: 초기 멀티캠 결과.
- `sofa-confrontation-natural-walk.mp4`: 접지·회전 문제를 사용자가 지적한 보행 버전.
- `sofa-confrontation-grounded.mp4`: 접지를 강조했지만 회전이 과도하게 분절된 버전.
- `sofa-confrontation-ensemble.mp4`: 다인 반응 추가 후 동시 팔 상승 문제가 남은 버전.
- `sofa-confrontation-subtle-reactions.mp4`: 손을 허벅지에 유지하고 반응을 절제한 버전.
- `sofa-confrontation-fluid-walk.mp4` 및 대응 `.blockshot.json`: 루트 속도 연속성과 발 구름을 개선한 최신 결과.

최신 결과도 사람이 검토한 한 사례이며, 엔진 일반 성능의 벤치마크나 모든 리그에서의 품질 보증으로 간주하지 않는다.
