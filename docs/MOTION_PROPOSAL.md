## 1. 제안의 핵심

**동작 프리셋의 종류를 늘리기보다, 다양한 연출을 동일한 신체·접촉·시간 관계로 표현하고 검증하는 공통 기반을 우선 구축한다.**

**상위 제품 요구사항:** 자연어 연출을 배우별 행동과 카메라 계획으로 구체화하고, 접촉과 사건 관계를 보존하면서 수정 가능한 프리비즈를 생성한다. 선언한 지원 범위에서 준비된 Blender 제작 환경과 동등한 품질을 유지하면서 승인까지의 사용자 개입·시간·토큰을 줄이는 것을 목표로 한다.

접촉 오차가 작다는 사실만으로 자연스러운 움직임이라고 판정하지 않는다. 이 문서의 출시는 **신체 타당성, 움직임·연기의 품질, 수정 보존성, 제작 효율**을 모두 검증해야 한다. Blender의 모든 모델링·시뮬레이션·최종 실사 렌더 기능과 동등해지는 것은 범위에 포함하지 않는다.

사용자는 “화를 참다가 일어나 몇 걸음 나간 뒤, 돌아서서 두 사람을 따진다”처럼 지시한다. 이 지시를 특정 동작 이름들의 조합으로만 번역하면, 접지·균형·연기 연결·상대 배우의 반응을 에이전트가 매번 수작업으로 보정하게 된다.

권장 처리 구조:

```text
사용자의 자연어 연출
  → 편집 가능한 연출 계획: 의도·주의 대상·사건·유지 조건
  → 동작 계획: 이동·지지 전환·접촉·타이밍
  → 움직임 생성 기반: 절차적·모션 자산·학습 방식 중 선택 또는 결합
  → 리그별 전신 보정과 접촉·관절 제약 풀이
  → 결정론적 평가 및 접촉·연속성 검사
  → 실제 렌더 검토
  → 원하는 부분만 수정하고 재계산
```

자연어 해석과 연출 선택은 유연하게 두되, 리그 해석·접촉 유지·시간 연결·재계산의 규칙은 엔진이 책임지는 구조를 제안한다. 초기 구현부터 물리 시뮬레이터나 학습 모델이 필수인 것은 아니다.

첫 지원 범위는 평탄한 실내, 선언된 휴머노이드 리그, 1~3명 배우, 10~30초 장면, 좌석·바닥·손에 드는 단순 소품, 다중 카메라 편집으로 제안한다. 계단·곡예·격투·복잡한 군중·옷감 접촉은 별도 확장 범위다. 범위 밖 요청은 지원 여부와 대안을 반환하며, 지원하지 않는 결과를 성공으로 표시하지 않는다. 범위 안에서는 미리 등록한 문구나 동작 목록에만 반응해서는 안 된다.

## 2. 관찰 범위와 책임 구분

이 문서는 연결된 MCP 도구, 실제 생성된 장면과 MP4, 로컬 설치 번들에서 확인한 구현을 바탕으로 한다. 전체 저장소·개발 브랜치·미공개 기능을 조사한 결과는 아니다. “미노출”은 이번 세션에서 사용 가능한 MCP 계약에 없었다는 뜻이며, 제품 전체에 해당 기능이 없다고 단정하지 않는다.

이번 제작은 **기존 리그를 사용했다.** 새 캐릭터 리그나 모션캡처를 도입하지 않았다. 기존 관절에 회전·골반·위치 트랙을 작성했고, 후반에는 실제 리그 치수를 읽어 발의 목표 위치에서 다리 각도를 역산했다. 확인된 기준 신장은 1.72m, 허벅지 관절 간 길이는 0.44m, 종아리는 0.41m였다. 이는 해당 리그의 값이며 모든 모델에 적용할 상수가 아니다.

문제에는 에이전트의 작성 실수도 포함된다. 초기에는 실제 치수와 다른 값으로 계산했고, 몸의 위치를 걸음마다 감속시키는 곡선을 사용했으며, 세 배우의 반응을 비슷한 시점에 배치했다. 따라서 제안 목표는 “엔진이 모든 연출을 대신 선택한다”가 아니라 **작성자가 실수하기 어려운 계약과, 실수를 발견·수정하기 쉬운 도구**를 제공하는 것이다.

## 5. P0-A — 공식 리그·표면·상태 조회

### 엔진 요구사항

- 관절 계층, 바인드 변환, 길이, 회전 순서, 축, 한계, 캐릭터 스케일을 반환한다.
- 발뒤꿈치·앞꿈치·발바닥·손바닥 같은 기준점과 접촉 면적을 제공한다.
- 허벅지·좌석·팔걸이처럼 접촉 대상으로 쓸 표면을 안정적인 ID로 노출한다.
- 지원하지 않는 관절·접촉 기준점은 추정값과 구분해 표시한다.
- 자유로운 리그 이름을 `left_foot`, `pelvis` 등의 의미 역할에 매핑하되 원본 ID를 보존한다.

### 제안 MCP

| 도구 | 주요 입력 | 주요 출력 |
|---|---|---|
| `get_capabilities` | 요청할 스키마 버전 | 지원 제약·리그 기능·평가·렌더 옵션, 엔진 버전 |
| `inspect_rig` | 장면 참조, 배우 ID | 관절·축·한계·치수·접촉 패치·바인드 상태 |
| `inspect_surfaces` | 장면 참조, 객체 ID 목록 | 표면 ID·변환·영역·충돌 지원 범위 |
| `evaluate_motion` | 장면 참조, 구간·샘플률·대상 | 관절/접촉점의 월드 변환, 속도, 활성 제약·접촉 |

`evaluate_motion`은 현재 `evaluate`의 확장으로 구현해도 된다. 특히 **발 위치·발바닥 방향·속도**를 선택적으로 조회할 수 있어야 한다. 데이터가 많으면 요약·구간 페이지·다운로드 아티팩트로 나누고, 수천 프레임을 기본 응답에 모두 넣지 않는다.

### 완료 기준

- 동일 장면·엔진 버전·리비전에서 평가와 렌더가 같은 골격 상태를 사용한다.
- 관절 이름을 모르는 에이전트가 공식 조회만으로 발바닥과 손바닥을 식별할 수 있다.
- 신장·다리 비율을 바꿔도 하드코딩한 기본 리그 길이에 의존하지 않는다.

## 6. P0-B — 진단은 점수보다 원인과 위치를 반환

### 진단 항목

- **접촉 이동:** 지지 구간의 접촉점이 기준 표면에서 이동한 거리.
- **관통·이격:** 접촉 모드에 맞는 발/손 표면과 대상 표면 사이 거리.
- **연속성:** 위치·속도·가속도·각속도의 급격한 변화와 발생 구간.
- **관절 한계:** 한계 초과, 도달 불가능한 목표, 지나친 보정량.
- **지지 상태:** 지지 영역과 몸의 무게중심 추정의 관계. 질량 모델이 없는 경우 운동학적 근사라고 표시한다.
- **렌더 가시성:** 중요 배우의 얼굴·손·발이 다른 객체나 프레임 경계에 가려지는 구간.
- **다인 동시성:** 연출상 연결되지 않은 배우들의 큰 제스처가 동시에 시작하는 구간. 오류 확정이 아닌 검토 경고로 제공한다.

### 제안 MCP

`analyze_motion(scene, range, profiles, tolerances)` → 구조화된 진단 목록, 관련 ID·구간·측정값·기준값·권장 수정 방향.

`render_review(scene, range, cameras, overlays, sampling)` → 실제 렌더의 정속/슬로모션 영상, 접촉·궤적 오버레이, 대표 프레임.

골격 프리뷰와 실제 렌더 결과를 명확히 구분한다. 접촉점만 맞았다고 메시 표면까지 맞았다고 보고하지 않는다. foot-lock 오차가 작아도 리듬·회전·상대 반응이 자연스러운지는 별도 시각 검토가 필요하다.

### 완료 기준

- 알려진 미끄러짐·관통·급정지 fixture를 주입하면 대상과 구간을 반환한다.
- 이동 중인 발을 지지 발로 오인하지 않으며, 앞꿈치 피벗을 평발 미끄러짐으로 오인하지 않는다.
- 검사 불가 항목은 `not_evaluated`와 이유를 반환한다.

## 7. P0-C — 접촉과 지지 상태를 보존하는 제약 풀이

### 공통 제약

| 제약 | 역할 | 이번 사례의 적용 |
|---|---|---|
| `contact` | 두 표면 사이 위치·방향·허용 자유도 유지 | 지지 발–바닥, 손바닥–허벅지 |
| `support` | 어떤 접촉이 몸을 지지하는지 지정 | 일어서기·걷기·회전의 지지 전환 |
| `look_at` | 머리·목·눈의 가능한 범위에서 주의 대상 추적 | 걸어 나가는 사람 따라보기 |
| `reach` | 접촉 전 접근·도달 목표 | 손을 무릎에 내려놓기 |
| `joint_limit` | 리그 관절 한계 준수 | 무릎·발목의 비정상 회전 방지 |
| `preserve` | 승인한 궤적·자세·접촉·구간 보호 | 다른 배우의 손 위치 보존 |
| `clearance` | 충돌·관통 회피 | 소파에서 일어나 앞 공간으로 이동 |

`contact`에는 기준 좌표계가 필요하다. 바닥 접지는 월드/바닥 로컬 기준, 손–허벅지 접촉은 움직이는 신체 표면 로컬 기준이다. 모델 스케일·표면 회전·상체 변화에도 의미가 유지되어야 한다.

접촉 모드는 최소한 **평발, 뒤꿈치, 앞꿈치 피벗, 비접촉**을 구별한다. 회전을 전부 금지하면 뒤돌기가 부자연스러워진다. 모드별로 접촉 영역과 허용 회전·미끄러짐을 지정하고, 전환 구간을 블렌드한다.

### 제안 MCP

`solve_motion(scene, range, constraints, objectives, preserve, seed)`

반환값은 수정된 장면 리비전 또는 패치, 풀이 상태, 제약 잔차, 접촉 일정, 평가 결과를 포함한다. 목표를 달성할 수 없으면 조용히 무시하지 않는다. 어떤 조건끼리 충돌하는지와 시간·도착 위치·접촉 중 무엇을 완화할 수 있는지 반환한다.

우선순위가 다른 조건을 구분한다. 예를 들어 바닥 관통 금지는 강한 조건이고, “0.1초 안에 돌아서기”는 도달 불가능할 때 조정 가능한 연출 목표일 수 있다. 자동 완화는 요청에 명시된 항목만 허용한다.

### 완료 기준

- 상체 기울기를 바꿔도 손바닥–허벅지 접촉이 허용 오차 안에 남는다.
- 리그 스케일·골반 높이·이동 속도를 바꿔도 지지 발의 접촉이 유지된다.
- 앞꿈치를 축으로 돌아설 때 발바닥 전체 고정을 강제하지 않는다.
- 실행 불가능한 조건 조합은 `infeasible`과 원인 목록을 반환한다.

## 8. P1-A — 이동과 보행을 공동 계획

보행 포즈와 루트 이동을 서로 독립적으로 작성하는 대신, 목적지·도착 구간·속도 성향·가용 공간·리그·접촉 조건에서 발 디딤과 몸 이동을 함께 산출한다.

사용자 입력은 “두 걸음으로 급히”, “망설이며”, “한쪽 다리에 무게를 덜 싣고”처럼 열려 있을 수 있다. 내부 표현은 발 디딤 위치, 지지 시간, 허용 하중, 발 방향, 관절 가동 범위, 선호 속도·보폭 등의 연속적인 값과 제약으로 정규화한다.

예를 들어 팔자걸음은 발의 선호 진행각과 고관절 회전 특성으로, 한쪽 다리의 불편함은 지지 시간·하중·가동 범위의 비대칭으로 표현할 수 있다. 이 표현만으로 모든 임상적 보행을 정확히 재현한다고 보장하는 것은 아니며, 해당 표현을 생성·보정·검증하는 공통 계약이 목적이다.

### 제안 MCP

`plan_motion`은 선택된 연출을 해석 가능한 계획으로 반환한다. 계획에는 경로, 속도 곡선, 지지/이동 단계, 발 디딤 후보, 예상 사건이 포함된다. `solve_motion`은 그 계획을 리그에 적용한다. 두 단계는 하나의 도구 내부에서 실행할 수 있지만, 계획 자체는 조회·수정할 수 있어야 한다.

이 계획만으로 연기의 자연스러움이 보장되지는 않는다. 계획에 맞는 전신 움직임을 생성하고 보정하는 필수 계약은 §15에서 정의한다.

### 완료 기준

- 거리·도착 시간 변경 시 보폭이나 걸음 수를 재계산한다.
- 의도한 망설임이 아닌 구간에서 걸음마다 루트 속도가 0으로 떨어지지 않는다.
- 급정지·느린 출발·비대칭 지지 같은 변형을 동일한 제약 체계로 처리한다.
- 좁은 공간 때문에 목표를 달성할 수 없으면 대안과 변경량을 반환한다.

## 9. P1-B — 사건 기반 시간 그래프

절대 시간은 지원하되, 주요 연기와 편집은 사건에 연결할 수 있도록 한다.

```text
stand.begin
  → left.notice (+ 짧은 지연)
  → walk.first_contact
  → walk.final_settle
  → turn.begin (+ 망설임)
  → turn.face_partner
  → point.begin
  → camera.cut_to_reaction
```

사건은 계획 단계의 예상값과 최종 풀이 이후의 확정값을 구분한다. 발 디딤 수가 바뀌어 중간 사건이 사라지더라도 `final_settle` 같은 의미적 앵커는 유지할 수 있어야 한다.

### 제안 MCP

- `inspect_timeline`: 사건·액션·컷의 관계와 현재 확정 시간을 조회.
- `retime`: 도착 시간이나 구간 길이를 수정하고 종속 요소를 재계산.
- `patch_scene`: 사건 참조를 포함한 편집을 리비전 단위로 적용.

### 완료 기준

- 걷기를 늘리면 회전·손가락질·리액션 컷이 정의한 관계에 맞게 이동한다.
- 사건 ID를 보존하고, 끊어진 참조와 시간 의존 순환을 오류로 반환한다.
- “먼저 보기 → 몸 돌리기 → 발 옮기기”의 선후관계를 유지한다.

## 10. P1-C — 부분 재생성, 잠금, 레이어 우선순위

사용자는 “다른 건 그대로 두고 걷기만”이라고 지시할 수 있어야 한다. 이때 무엇이 실제로 보존되는지 명확해야 한다.

- 보호 범위: 배우, 신체 부위, 접촉 관계, 카메라, 구간, 사건.
- 재계산 영향 범위: 변경으로 인해 조정이 필요한 요소를 미리 반환.
- 원자적 적용: 기대 리비전과 맞을 때만 패치를 적용.
- 되돌리기와 후보 분기: 이전 장면으로 복원하거나 A/B 비교.
- 우선순위: 수동 키프레임, 제약, 절차적 모션, 제스처가 충돌할 때 승자와 이유를 조회.

현재도 액션 삭제·수정과 트랙 기반 보정이 가능하다. 제안은 이를 대체하기보다, **풀이 대상·보호 조건·충돌 진단이 포함된 재생성 계약**을 추가하는 것이다.

잠금과 새 목표가 양립하지 않으면 보호된 결과를 몰래 수정하지 말고 충돌을 반환한다. 양팔이 잠겼는데 팔 동작이 필요한 균형 보정을 요청한 경우가 예다.

## 11. P1-D — 배우별 상태와 인과적인 반응

배우마다 다음 상태를 유지한다.

- 현재 자세와 유지할 접촉
- 현재 주의 대상
- 행동 의도와 반응의 원인
- 움직여도 되는 부위와 움직임의 크기
- 이미 진행 중인 행동과 중단 가능한 시점

“반응하라”를 큰 제스처로 바로 번역하지 않는다. 예를 들어 `hands_resting`, `attention_to_partner`, `small_posture_adjustment`는 특정 연기 이름보다 지속 상태에 가깝다. 사용자는 내부 명칭을 알 필요 없이 “손은 그대로 두고 고개만 따라가”라고 수정할 수 있다.

### 제안 MCP

`plan_performance(scene, direction, actor_context, preserve)` → 배우별 의도, 주의 대상, 사건 연결, 허용 움직임, 선택한 해석과 대안.

이 단계는 확률적인 자연어 해석을 포함할 수 있다. 그러나 선택된 계획은 저장되어야 하며, 이후 `solve_motion`은 버전과 seed를 고정해 재현 가능해야 한다. 모든 호출에서 장면 전체를 새로 해석하지 않는다.

배우의 상태와 반응을 장면 전체의 의도·카메라 편집에 연결하는 상위 계획 계약은 §16을 따른다.

### 완료 기준

- “계속 듣기”를 무동작 또는 미세한 시선·자세 반응으로 표현할 수 있다.
- 상대가 움직이기 전에 원인 없는 큰 반응이 먼저 시작되지 않는다.
- 동시 동작을 원하지 않는 지시에서 여러 배우가 같은 시점에 손을 들지 않는다.
- 손 접촉을 유지하면서 서로 다른 몸·고개 반응을 만들 수 있다.

## 12. 제안 MCP 계약 예시

아래 이름·필드는 **신규 인터페이스 제안**이며 현재 지원되는 호출이 아니다. 계약을 논의하기 위한 예시로, 완전한 JSON Schema는 아니다.

### 접촉을 유지한 보행 계획과 풀이

```json
{
  "tool": "solve_motion",
  "arguments": {
    "schemaVersion": "proposed-1",
    "sceneRef": {"id": "sofa-scene", "revision": 12},
    "actor": "center",
    "range": {"fromEvent": "stand.end", "toEvent": "walk.final_settle"},
    "planRef": "plan-walk-03",
    "constraints": [
      {"id": "floor-clearance", "type": "clearance", "subject": "center", "surface": "floor", "priority": "required"},
      {"id": "stance-contact", "type": "contact_schedule", "scheduleRef": "plan-walk-03.contacts", "priority": "required"},
      {"id": "joint-limits", "type": "joint_limit", "source": "rig", "priority": "required"}
    ],
    "objectives": {"continuousRootVelocity": true, "minimizePoseChange": true},
    "preserve": [
      {"actors": ["left", "right"], "scope": "all"},
      {"scope": "camera_geometry"}
    ],
    "allowedRelaxations": ["arrival_time"],
    "seed": 7
  }
}
```

접촉 조건은 항상 발바닥 전체를 고정하는 대신, 계획이 반환한 접촉 스케줄을 참조한다. 손·발·표면 식별자는 `inspect_rig`와 `inspect_surfaces`의 반환값을 사용하며 이름을 추측하지 않는다.

### 손–허벅지 접촉 유지

```json
{
  "id": "left-hand-rest",
  "type": "contact",
  "subject": {"actor": "left", "patch": "palm_left"},
  "target": {"actor": "left", "surface": "thigh_left"},
  "frame": "target_local",
  "mode": "rest",
  "active": {"fromEvent": "scene.begin", "toEvent": "scene.end"},
  "tolerances": {"separationMeters": 0.005},
  "priority": "required"
}
```

### 구조화된 결과와 실패

```json
{
  "status": "solved",
  "sceneRef": {"id": "sofa-scene", "revision": 13},
  "engineVersion": "<reported-by-runtime>",
  "solverVersion": "<reported-by-runtime>",
  "patchRef": "patch-13",
  "changed": {"actors": ["center"], "rangeSeconds": [1.7, 4.8]},
  "events": {"walk.final_settle": 4.8},
  "relaxed": [{"field": "arrival_time", "deltaSeconds": 0.2}],
  "diagnostics": [],
  "artifacts": [{"kind": "motion_report", "ref": "report-13"}]
}
```

`solved`는 허용 조건을 만족한 풀이 결과이며 예술적으로 자연스럽다는 보증이 아니다. 실패 시 `infeasible`, `unsupported`, `revision_conflict` 등을 구분하고 `constraintIds`, `range`, `reason`, `suggestedRelaxations`를 반환한다. 임계값 초과 진단을 숨긴 채 성공으로 처리하지 않는다.

## 13. API 운영·호환성 원칙

- 기존 `run_script`, `apply_addon`, `evaluate`, `preview`, `render_video`, `open_link` 흐름은 유지한다.
- 사람이 읽는 설명과 별개로, 장면·패치·진단은 MCP의 구조화된 결과로 반환한다. 설명 텍스트에서 `spec:` 이후를 잘라 파싱하지 않아도 되어야 한다.
- 작은 작업은 inline spec, 큰 작업은 장면/아티팩트 참조를 지원한다. 고밀도 관절 트랙을 매번 대화 컨텍스트로 왕복시키지 않는다.
- 좌표계, 거리 단위, 각도 단위, 회전 순서, 시간 기준을 계약에 명시한다.
- 해결기·엔진·리그 버전과 seed를 기록한다. 학습 모션을 사용하면 모델·클립 버전도 기록한다.
- 긴 렌더/풀이에는 job ID, 단계, 취소, 재연결 가능한 상태 조회를 제공한다. 완료 전 파일이 존재한다고 가정하지 않는다.
- 액션·제약·사건에 안정적인 ID를 부여한다. 배열 위치 기반 이름에만 의존하지 않는다.
- 결과에는 승인하지 않은 변경, 자동 완화, 평가하지 못한 항목을 명시한다.

## 14. 회귀 시나리오와 제안 수용 기준

다음 수치는 개발 논의를 위한 **초기 허용치 제안**이다. 실제 리그·메시·렌더 정확도로 검증해 조정해야 한다.

| 시나리오 | 자동 검증 | 시각 검토 |
|---|---|---|
| 세 사람의 소파 장면 | 모든 사건 참조 유효, 보호된 두 배우의 발·손 접촉 보존 | 원인 없는 동시 손짓 없음, 주인공의 이동에 대한 개별 반응 |
| 거리·시간 변경 보행 | 필수 정지가 없는 중간 접촉에서 루트 속도 불연속 검사 | 걷다 서다 반복하지 않음 |
| 다른 신장·다리 비율 | 지지 접촉점 이동/이격 각각 5mm 이내를 초기 목표로 설정 | 발이 뜨거나 바닥을 통과해 보이지 않음 |
| 앞꿈치 피벗 | 피벗 접촉 유지, 허용 회전 준수, 무릎 한계 준수 | 평발 회전이나 잔걸음 반복처럼 보이지 않음 |
| 손을 둔 채 몸 기울이기 | 신체 로컬 표면 접촉 유지 | 손이 허공에 뜨거나 허벅지를 뚫지 않음 |
| 도착 시간 재지정 | 종속 사건·컷 재타이밍, 참조 손실 없음 | 회전·항의·리액션의 순서 유지 |
| 불가능한 시간·잠금 조합 | `infeasible`, 충돌 조건·대안 반환 | 무리한 관절 꺾임으로 억지 해결하지 않음 |
| 특정 구간만 재생성 | 보호 대상의 트랙/평가값 변경 없음 | 앞뒤 연결이 튀지 않음 |

검사 기준은 접촉 유형별로 다르게 적용한다. 스윙 발은 바닥에서 떠 있어야 하고, 피벗 발은 회전할 수 있다. 동적인 균형을 단순한 정적 지지다각형 규칙으로 무조건 금지해서도 안 된다.

## 15. 필수 — 움직임 생성 기반

### 15.1 요구사항과 구현 선택권

제약 풀이가 “가능한 자세”를 만드는 기반이라면, 움직임 생성은 “사람처럼 이어지는 움직임”을 만드는 기반이다. 양쪽을 별도 책임으로 두되 함께 검증한다.

| ID | 필수 요구사항 | 확인 방법 |
|---|---|---|
| MG-01 | 경로·의도·현재 상태·리그·환경·접촉 조건에서 전신 움직임을 생성한다. | 관절 키를 사용자가 직접 주지 않아도 장면을 완성 |
| MG-02 | 출발·이동·정지·회전·주의 전환 사이의 자세·속도·각속도 연결을 관리한다. | 의도하지 않은 정지·스냅·팔다리 위상 불일치 검사 |
| MG-03 | 골반·상체·팔·머리의 선후관계와 비대칭을 상황에 맞게 생성한다. | 단순 동일 위상 사인파와 구별되는 블라인드 품질 평가 |
| MG-04 | 속도, 선호 보폭, 발 방향, 지지 비대칭, 상체 자유도 등 연속 특성을 제약 안에서 조합한다. | 보지 못한 조합에 대한 평가; 이름별 전용 분기 없이 수행 |
| MG-05 | 리그별 길이·축·한계에 맞게 적용하고 결과의 접촉·가동 범위를 재검사한다. | 신장·신체 비율이 다른 지원 리그의 전이 평가 |
| MG-06 | 진입·종료 상태 및 보존 구간을 받아 일부 구간만 생성한다. | 생성 구간 앞뒤의 연속성 및 잠금 보존 검사 |
| MG-07 | 같은 환경에서 재현 가능한 결과와 생성 출처를 저장한다. | 백엔드·모델/클립·리그·solver 버전·seed 기록 및 재실행 |
| MG-08 | 생성 후 보정으로 움직임의 특징이 훼손되면 알린다. | 보정 전후 변화량, 실패 조건, 대안 반환 |

허용 구현은 절차적 생성+전신 풀이, 모션 자산의 검색·변형·연결, 학습 기반 생성+제약 보정, 또는 혼합 방식이다. 단일 기술을 요구하지 않는다. 내부에서 모션 자산을 재사용해도 되지만, 외부 계약을 고정된 연기 이름의 목록으로 제한하지 않는다. 자산의 사용·배포 권한과 버전도 출처 기록에 포함한다.

접촉을 만족하기 위해 보폭을 바꾼 결과 목적지에 늦게 도착하는 등 목표 간 충돌을 명시한다. 보정 과정이 연출 의도나 잠금 조건을 무단으로 바꾸면 실패다.

### 15.2 제안 MCP 계약

`generate_motion(sceneRef, performancePlanRef, motionPlanRef, actorIds, range, boundaryStates, constraints, preserve, backendPolicy, seed)`

반환: `motionCandidateRef`, 접촉 일정, 예상/확정 사건, 생성 출처, 지원하지 않는 조건, 보정 필요 항목, 진입·종료 상태. 이후 `solve_motion`이 후보를 보정한다. 통합 구현에서는 한 호출로 생성·풀이하되 두 단계의 진단을 구분한다.

기본 반환은 후보 하나와 간결한 진단이다. 복수 후보는 요청된 예산 안에서만 만들고, 선택하지 않은 후보의 생성·검토 비용도 로그에 남긴다. 저품질 후보를 사용자에게 숨겼더라도 총비용에서는 제외하지 않는다.

`get_capabilities`에는 지원 리그, 경계 상태 조건, 접촉 모드, 생성 백엔드, 결정론적 재실행 가능 범위를 포함한다. 외부 모델의 비결정성이 있으면 seed만으로 재현된다고 주장하지 말고 생성 아티팩트를 고정해 재사용한다.

### 15.3 완료 기준

- “목적지는 같게, 더 조심스럽게”, “한 손의 컵을 유지하며”, “멈추려다가 계속 가기”를 지원 범위 안에서 동일한 계획·제약 구조로 처리한다.
- 단순 속도 배율 변경으로 발을 미끄러뜨리지 않고 접촉 일정과 몸 이동을 함께 수정한다.
- 정밀 접촉 검사와 §17의 자연스러움 평가를 각각 통과한다. 어느 하나로 다른 하나를 대체하지 않는다.
- 기술 기능만 구현한 상태가 아니라, 준비된 Blender 기준과 비교할 수 있는 렌더 결과를 제출한다.

## 16. 필수 — 연출 계획 능력과 수정 계약

### 16.1 계획이 해야 하는 결정

계획은 원문, 해석, 선택한 행동, 선택 이유, 사건 의존 관계를 연결한다. 사용자에게 관절·발 디딤 수치 입력을 강요하지 않는다.

| ID | 필수 요구사항 | 사례 |
|---|---|---|
| DP-01 | 원문에 명시된 조건과 시스템이 정한 가정을 구분한다. | ‘갑자기’는 지시, 이동 거리와 주시 순서는 선택한 해석 |
| DP-02 | 배우별 의도·주의·지속 상태·행동 원인을 계획한다. | 주인공은 항의, 왼쪽은 경계, 오른쪽은 늦게 상황 파악 |
| DP-03 | 행동과 반응을 사건에 연결하며, 무반응/미세 반응도 유효하게 취급한다. | 손은 유지하고 상대를 따라보기 |
| DP-04 | 카메라 계획을 전달할 정보와 사건에 연결한다. | 기립은 동작을 읽는 구도, 반응은 해당 인물이 인지한 뒤 컷 |
| DP-05 | 모호한 수정 지시를 구체적 변경과 보존 조건으로 변환한다. | ‘더 화나게’의 해석을 출발 속도·정지 시간·시선 선택으로 명시 |
| DP-06 | 전체를 새로 해석하지 않고 승인한 계획을 부분 수정한다. | 걷기만 수정하면 나머지 배우와 승인된 컷 의도 유지 |
| DP-07 | 원문→계획→생성→진단의 추적 관계를 보존한다. | 왜 손을 들었는지 또는 왜 컷이 이동했는지 조회 |
| DP-08 | 실행 가능성을 확인하고 불가능한 지시를 숨기지 않는다. | 공간 부족·잠금 충돌이면 영향과 대안을 반환 |

모호함이 있어도 결과를 해치지 않는 일상적 결정은 가정으로 기록하고 진행한다. 상반된 장면 의미를 만들거나 필수 조건을 깨는 결정에 한해 질문 또는 명확히 구분된 대안을 제시한다. 매 단계 확인을 요구하는 인터페이스를 기본으로 하지 않는다.

### 16.2 공통 중간 표현

계획에는 다음 필드를 포함한다: `sourceDirection`, `assumptions`, `actorIntent`, `attention`, `persistentConstraints`, `beats`, `eventDependencies`, `cameraIntent`, `preserve`, `alternatives`, `provenance`.

`beat`는 사용자가 말한 행동의 의미와 사건 관계를 보존하는 단위다. 내부 의미 역할은 정규화할 수 있지만, 사용자가 정해진 단어를 사용해야만 성공하도록 만들지 않는다. 복합 지시를 처리할 수 있어야 한다.

### 16.3 MCP 인터페이스와 예시

- `plan_performance`: 선택한 해석과 근거를 포함한 버전 있는 계획 생성.
- `inspect_plan`: 배우·사건·원문별로 필요한 부분만 조회.
- `revise_plan`: 자연어 수정으로 계획 패치 및 영향 범위를 생성. 기본은 미적용 패치이며 `apply: true`로 원자적 적용 가능.
- `compare_candidates`: 요청한 후보의 연출 차이·동작 진단·비용·미리보기 반환.

아래는 신규 인터페이스 제안이다.

```json
{
  "tool": "revise_plan",
  "arguments": {
    "sceneRef": {"id": "sofa-scene", "revision": 13},
    "performancePlanRef": {"id": "performance-03", "revision": 2},
    "direction": "가운데 사람은 망설이지 말고 나가되, 두 사람의 손은 계속 무릎에 두고 반응은 작게 유지해줘.",
    "preserve": [
      {"actors": ["left", "right"], "scope": "hand_contacts"},
      {"scope": "camera_intent"}
    ],
    "apply": false
  }
}
```

반환에는 선택한 해석, 변경할 beat·사건·배우, 보호 대상, 재생성할 구간, 카메라 시간에 미치는 영향, 예상 추가 작업, 충돌 조건을 포함한다. `camera_intent` 보존은 절대 컷 시각 고정과 다르다. 의도와 사건 연결을 보존하면서 시간을 옮길 수 있으며, 절대 시각 잠금은 별도 범위로 요청한다.

### 16.4 완료 기준

- 초안 계획의 주요 결정을 간결한 문장으로 설명할 수 있고, 장면 결과에서 그 결정을 추적할 수 있다.
- 첫 장면에서 배우별 자세·주의가 구분되고, 원인 없는 동시 큰 제스처가 나타나지 않는다.
- ‘걷기만’, ‘손은 그대로’, ‘컷은 유지’ 같은 부분 수정이 의도대로 적용된다.
- 연출 충실도는 계획의 텍스트만이 아니라 최종 MP4로 평가한다.

## 17. 필수 — 준비된 Blender 제작 환경 대비 수용 기준

### 17.1 비교 대상과 공정한 조건

‘Blender보다 좋다’는 프로그램 전체 기능의 비교가 아니다. 아래 조건을 고정한 **승인 가능한 프리비즈를 만드는 작업 흐름**의 비교다. 현재 두 환경의 대조 실험을 수행한 것은 아니며, 아래는 실행할 시험 계획이다.

1. **운영 기준선:** 검증된 휴머노이드 리그, IK·접촉 컨트롤, 모션 재사용, 카메라·렌더 템플릿, 부분 수정 스크립트가 준비된 Blender MCP 환경. 동일 모델·추론 설정의 에이전트가 작업한다. Blockshot에도 자체 재사용 기반과 같은 준비 예산을 허용한다.
2. **품질 참고선:** 필요하면 숙련 애니메이터의 Blender 결과를 별도 확보한다. 사람의 작업 시간·비용을 측정하지 않고 이를 에이전트 비용 기준선과 섞지 않는다.
3. **고정 조건:** 원문 지시, 배치·리그에 접근 가능한 정보, 길이, 해상도·FPS, 카메라 요구, 하드웨어/자원 상한, 평가용 마네킹·재질·조명 수준을 맞춘다. 불가피한 차이는 기록한다.
4. **리그의 공정성:** 의미 역할·치수·변형 메시를 동등하게 제공한다. 각 엔진의 컨트롤 구현까지 동일하게 강제하지 않는다. 사용할 수 없는 리그를 한쪽에서 조용히 교체하지 않는다.
5. **범위 고정:** §1의 지원 범위를 먼저 선언한다. 평가 실패 후 특정 장면을 범위 밖으로 재분류해 성적을 개선하지 않는다.

### 17.2 시험 구성

초기 평가 묶음은 40개 과제(공개 개발 과제 20개, 미공개 일반화 과제 20개), 과제별 3회 실행으로 제안한다. 최종 규모는 파일럿의 분산과 목표 검정력에 따라 조정하되 본 평가 전에 고정한다. 40개가 항상 충분한 통계적 증거를 보장하지는 않는다.

과제군은 이동·정지·방향 전환, 기립·착석·접촉 유지, 손에 물건을 든 복합 동작, 다인 반응과 시선, 부분 수정·재타이밍의 다섯 범주로 균등 구성한다. 소파 장면은 공개 개발 과제 중 하나이며 단독 출시 시험이 아니다.

미공개 과제는 신체 비율, 가구 배치, 이동 거리, 지지 비대칭, 반응 순서, 복합 지시를 새롭게 조합한다. 동일 지원 토폴로지 안의 다른 리그 비율도 포함한다. 미공개 세트로 튜닝하면 해당 세트를 폐기하고 새 세트로 교체한다.

평가에는 첫 결과와 수정 후 결과를 모두 포함한다. 양쪽에 동일한 최대 사용자 수정 횟수(초기안: 3회)와 작업 예산을 준다. 사용자 피드백은 같은 평가 규칙에 따라 각 결과의 문제를 지적하며, 한쪽에만 해결 코드를 제공하지 않는다. 자동 내부 재시도와 후보 생성은 허용하되 모두 비용·시간에 포함한다. 한도를 초과한 결과는 실패로 남긴다.

### 17.3 측정할 항목

| ID | 지표 | 정의 |
|---|---|---|
| QA-01 | 첫 결과 승인율 | 사용자 수정 전 최종 사용 가능한 결과의 비율. 내부 후보·재시도는 비용에 포함 |
| QA-02 | 최종 승인율 | 동일한 수정·시간 예산 안에 승인 기준을 만족한 과제 비율 |
| QA-03 | 동작·연출 품질 | 자연스러움, 연출 충실도, 배우 반응, 카메라 전달력, 동작 연결을 각각 평가 |
| QA-04 | 사용자 개입 | 승인까지 추가 지시 횟수, 수동 편집 시간, 블로킹 질문 수 |
| QA-05 | 전체 소요 시간 | 요청부터 결과 제공까지의 wall-clock. 계획·풀이·렌더·재시도·검토·수정 단계를 별도 기록 |
| QA-06 | 토큰·모델 비용 | 모든 호출의 입력·출력·캐시·제공되는 경우 추론 토큰과 실제 과금값. 실패·내부 후보 포함 |
| QA-07 | 계산·자산 비용 | 로컬/GPU 실행 시간, 외부 생성 비용, 자산 비용. 토큰 비용과 분리 |
| QA-08 | 수정 보존성 | 보호한 배우·접촉·구간·카메라 의도의 변경 여부, 수정 구간의 앞뒤 연결 |
| QA-09 | 일반화·재현성 | 미공개 과제 품질과 승인율, 반복 실행 분산, 버전 고정 시 재현 범위 |

토큰 수와 과금액을 구분한다. 같은 모델·가격표를 고정한 비교 비용도 보고하고 캐시 정책을 기록한다. 렌더 대기 시간은 그 자체가 토큰 사용량이 아니다. 제공되지 않는 토큰 항목은 `unavailable`로 표시하며 JSON 크기에서 실제 사용량을 역산하지 않는다.

실패한 작업도 비용 합계에 포함한다. 효율은 성공 과제의 중앙값만 보고 끝내지 않고, 전체 시도 비용/승인 결과 수와 실패율을 함께 보고한다. 공통 승인 과제의 짝 비교, 전체 승인율, 초과시간/미완료 비율을 병행한다. 성공률이 낮은 시스템이 실패 작업을 제외해서 더 싸게 보이지 않게 한다.

초기 제작 기반 구축 비용은 장면당 반복 비용과 분리한다. `초기 구축 + N개 장면의 실행·수정`을 N=1, 10, 50으로 보고한다. 준비된 Blender의 자산·자동화 구축 비용을 0으로 숨기거나, Blockshot의 개발 비용만 장면당 비용에 넣는 비교는 하지 않는다. 제품 R&D와 프로젝트별 준비 비용도 구분한다.

### 17.4 블라인드 품질 평가

- 평가자는 엔진 이름·개발 팀·생성 비용을 모르는 상태에서 같은 크기의 영상을 비교한다. 좌우·재생 순서를 무작위화한다.
- 과제당 최소 5명의 독립 평가자를 초기안으로 하며, 애니메이션/연출 검토 경험자를 포함한다. 평가자 구성과 의견 차이를 공개한다.
- 각 품질 축을 1~5점으로 평가한다: 1=목적 달성 불가, 3=동선 전달은 되지만 눈에 띄는 수정 필요, 5=지원 범위의 프리비즈로 수정 없이 승인 가능. 2와 4는 인접 수준 사이로 정의한다.
- 개별 결과 승인 기준 초기안: 필수 연출 누락·중대한 접촉/관통 오류 없음, 각 품질 축의 평가자 중앙값 4점 이상. 모든 평가자가 모든 축에 최고점을 주어야 한다는 뜻은 아니다.
- 정속 재생을 기본으로 하고, 느린 재생·접촉 오버레이는 원인 확인에 사용한다. 정적 대표 프레임만으로 자연스러움을 승인하지 않는다.
- 자동 진단, 블라인드 점수, 자유 서술 결함을 함께 보존한다. 하나의 ‘자연스러움 점수’로 전체를 압축하지 않는다.

### 17.5 출시 게이트 — 제안 목표치, 미달성 상태

다음은 개발팀과 파일럿 후 확정할 초기 목표다. 실제 성능 주장이나 이미 합의된 계약이 아니다. 품질 비열등성이 먼저이며, 빠른 저품질 결과는 효율 목표를 통과할 수 없다.

| 게이트 | 통과 조건 초기안 |
|---|---|
| G0 기능·타당성 | §14 회귀 검사 통과. 모든 보호 조건과 필수 연출 조건 준수. 숨겨진 필수 제약 완화 없음 |
| G1 품질 동등성 | 품질 축별 Blockshot−Blender 짝 차이의 95% 신뢰구간 하한 ≥ −0.25점(5점 척도). 최종 승인율 차이의 하한 ≥ −5%p. 독립 과제 기준으로 군집화해 반복 실행·평가자를 독립 표본처럼 부풀리지 않음 |
| G2 수정 보존성 | 테스트의 보호 조건 위반 0건. 단순 키프레임 동일성뿐 아니라 요청한 보존 범위의 평가값·사건 관계 검증 |
| G3 운영 경쟁력 | G1 통과 후, 전체 시도 비용/승인 결과 수 기준 정규화 모델 비용과 공통 승인 과제의 전체시간 중앙값 모두 Blender 이하. 사용자 추가 지시 중앙값도 이하 |
| G4 우위 주장 | G3에 더해 모델 비용 또는 시간 중앙값 중 하나 이상 30% 개선. 나머지 지표 및 P90 시간은 기준선보다 10% 이상 악화하지 않음. 불확실성 범위도 함께 보고 |
| G5 일반화 | 미공개 세트에 대해서도 G1/G2를 따로 확인. 과제군별 결과와 실패를 공개하고 낮은 품질을 전체 평균으로 숨기지 않음 |

신뢰구간이 넓어 조건을 판정할 수 없으면 `inconclusive`로 보고한다. 동등하다고 선언하지 않으며 추가 평가를 수행한다. 운영 지표도 짝 비교의 신뢰구간을 함께 제시한다. 표본이 부족한 세부 과제군에 대해서는 동등성 주장을 확대하지 않는다.

### 17.6 제출할 증거

실험 manifest에는 모델·엔진·리그·자산 버전, seed, 장비, 가격표, 캐시 정책, 지원 범위, 과제 분할, 실행 예산, 승인 규칙을 기록한다. 결과에는 첫/최종 MP4, 장면·계획·패치, 수정 대화, 모든 호출/렌더 작업의 사용량, 진단, 평가 원자료, 재현 명령을 포함한다. 미공개 과제는 평가 전 접근을 제한하고 평가 후 공개 범위를 정한다.

## 18. 개발 단계와 완료 산출물

| 단계 | 구현·검증 단위 | 완료 산출물/다음 단계 조건 |

| M1 전체 흐름 시제품 | 소파 장면의 계획→생성→접촉 보정→반응→카메라→MP4→부분 수정. MG/DP 최소 계약 포함 | 원본 및 ‘걷기만 수정’ 결과, 실제 렌더 검토, 실패/보정 보고. 기능 목록만으로 완료하지 않음 |

| M4 확장 | 다른 생성 백엔드, 더 다양한 공간·신체·후보 표현 | 새로운 지원 범위에 대한 별도 시험. G4 충족 범위에 한해 ‘더 우수’ 주장 |

한 장면만 잘 만들고 범용성을 주장하거나, 모든 기반 기능을 만든 뒤에야 자연스러움을 검토하는 두 방식을 피한다. **전체 흐름을 작은 범위에서 먼저 통과시키고, 수정 보존성과 미공개 변형을 통해 일반화한다.**

## 19. 사례 자료

워크스페이스에 보존된 아래 파일을 개발 검토 자료로 사용할 수 있다. 이 제안서를 외부에 전달할 때 필요한 영상만 별도로 첨부한다. 파일명은 식별용이며 개발자의 환경에 존재한다고 가정하지 않는다.

- `sofa-confrontation-drama.mp4`: 초기 멀티캠 결과.
- `sofa-confrontation-natural-walk.mp4`: 접지·회전 문제를 사용자가 지적한 보행 버전.
- `sofa-confrontation-grounded.mp4`: 접지를 강조했지만 회전이 과도하게 분절된 버전.
- `sofa-confrontation-ensemble.mp4`: 다인 반응 추가 후 동시 팔 상승 문제가 남은 버전.
- `sofa-confrontation-subtle-reactions.mp4`: 손을 허벅지에 유지하고 반응을 절제한 버전.
- `sofa-confrontation-fluid-walk.mp4` 및 대응 `.blockshot.json`: 루트 속도 연속성과 발 구름을 개선한 최신 결과.

최신 결과도 사람이 검토한 한 사례이며, 엔진 일반 성능의 벤치마크나 모든 리그에서의 품질 보증으로 간주하지 않는다.
